# Shipped recipes

Recipes the package ships, one `<id>.recipe.json` per recipe revision, validated by the `Recipe` schema in `src/services/architect/schemas.ts`. The catalog loads every `*.recipe.json` here and reports invalid files with their reason ([ARCH](../../dev/ARCH.md#decision-log), TODO 2.4).

Each output declares what one run writes for its role (`format`, `count`), so the contract layer can tell a task asking for another format or more images apart from one the recipe serves; a task field that no slot fills and no declaration covers stays a hard unknown. A change to a recipe bumps its `revision`: the catalog refuses a changed file under a revision it already holds.

## The set

The set of GAPS Q24 (TODO 5.4): Z-Image Turbo and FLUX.1-schnell, installed on the reference target, FLUX.2 Klein 4B distilled, Real-ESRGAN x4plus and SeedVR2 3B. Size rule: **task** means slots take the width and height from the task, and **multiple of n** that a task side off the latent's step fails the contract check (the output's `multipleOf`); **×n of input** means the output is that input's size times n (`scaleOfInput`), and the contract layer compares it with the task's size once it has read the input's dimensions from the target; **round to 8** means the graph rounds each side down to a multiple of 8, so an input whose product isn't one fails. A recipe marked **stretch check** scales the source to the task's size (`scalesInputToTask`) and gets a soft check when the aspect ratios differ by more than 1%. An inpaint recipe's mask must have the source image's size (a hard check), and a mask that doesn't decode to one channel gets a soft check: the graph reads its red channel.

An agent wrote every recipe marked `proposed`; the owner's review makes one `curated` (spec §8.4, GAPS Q27), and none claims a maintainer review it hasn't had. A review covers the revision it looked at (the evidence's `revision`); a review entry without one predates the field and is GAPS Q12's review of revision 3. The catalog refuses a shipped recipe whose tier its evidence doesn't support, and a revision `main` ships keeps its content (a test compares it with `fixtures/main-recipe-hashes.json`). The owner reviewed three recipes at revision 3 (GAPS Q12); `recipe-flux1-schnell.t2i` is unchanged since and stays `curated`. `recipe-zimage-turbo.t2i` gained pinned sources in revision 4, and `recipe-zimage-turbo.img2img` took an `input_image` slot and declares its output as the source's size in revision 5, so both are `proposed` again until the owner reviews the change. `recipe-flux1-schnell.ckpt-*` load FLUX.1-schnell from Comfy-Org's all-in-one checkpoint with `CheckpointLoaderSimple`, as ComfyUI's `flux_schnell` template does; the file has to be in `checkpoints/` (GAPS Q13).

Each recipe built from a ComfyUI template cites it in `evidence` (kind `documentation`) with its name, the template package version and the sha256 of the template as the target served it, and says what was kept, left out and changed. An input image is a file in ComfyUI's input folder, taken from the task (`input_image` slots, GAPS Q33); a mask is a separate image, white where the image is repainted, read from its red channel. The inpaint recipes put the repainted area over the source with `ImageCompositeMasked`, so the pixels outside the mask are the source's.

## Model files, sources and families

A recipe pins the source of each model file it can acquire in `modelSources`: folder, file name on disk, and a Hugging Face repository at a 40-character commit with the path, sha256 and size Hugging Face reports, written with `node scripts/architect/pin-source.mjs <repo> <path> [revision] --folder <folder> [--file <name>]` and never by hand. Planning reads them offline: a candidate whose only failing checks are model files with a pinned `.safetensors` source within the size limit is `acquirable` (ARCH 2026-11-16; GAPS Q25). Every recipe but `recipe-flux1-schnell.t2i` and `recipe-flux1-schnell.ckpt-t2i` pins all its files. The Z-Image files come from `Comfy-Org/Z-Image-Turbo` (requested as `Comfy-Org/z_image_turbo`, which Hugging Face redirects), RealESRGAN x4plus from `Comfy-Org/Real-ESRGAN`, the FLUX.1-schnell checkpoint from `Comfy-Org/Flux-1-Schnell`, FLUX.2 Klein 4B and its VAE from `Comfy-Org/Flux-2-Klein-4B`, the ControlNet patch from `alibaba-pai/Z-Image-Turbo-Fun-Controlnet-Union`, and SeedVR2 3B and its VAE from `Comfy-Org/SeedVR2`. Klein uses the installed Qwen 3 4B encoder, pinned from `Comfy-Org/Z-Image-Turbo`. The FLUX.2 Klein and SeedVR2 recipes bind the bf16 and fp16 files where ComfyUI's templates load fp8 or int8 ones, whose support on Apple GPUs is unverified (ARCH 2026-11-16, precision); the FLUX.1-schnell checkpoint is the installed fp8 one.

A model slot's `modelFamily` names a rule in `architect/families/`. Planning reads each bound file's safetensors header, never the weights, and checks it against the rules (TODO 5.3; GAPS Q14): a header that matches the slot's rule passes, one that matches another family's rule fails as a hard check, and an unread header or one no rule matches stays unknown, soft for the recipe's default file and hard for any other. On the reference target each installed file of the set matches its own rule and no other: `z_image_turbo_bf16`, `qwen_3_4b`, the Z-Image `ae.safetensors` (rule `flux-ae`, alias `z-image-vae`), the FLUX.1-schnell checkpoint and `RealESRGAN_x4plus`; the rules for the files not installed yet (`flux2-klein-4b`, `flux2-vae`, `z-image-controlnet-union`, `seedvr2-3b`, `seedvr2-vae`) were written from the files' headers read remotely with HTTP Range requests, and match none of the installed files; once a file is placed, planning reads its header like any installed file's. A header doesn't tell a distilled model from its base model with the same architecture (Z-Image Turbo from Base, Klein 4B distilled from Klein Base 4B), so the family check can't either.

Test fixtures, certification `fixture`, live in `src/__tests__/architect/fixtures/` and are never placed here.

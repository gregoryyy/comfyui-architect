# Approval channel for external MCP clients

Covers which channel can carry a user's approval of an effect (a render now, downloads and installs later) when the client is an external MCP client: Claude Code (CLI and VS Code extension) first, Codex CLI and Claude Desktop second. Serves spec §14.2 and §14.3, GAPS Q-entries on approval grants (none was found by keyword in `ext/GAPS.md`; the owner assigns the entry), and the later TODO items that implement `ApprovalGrant`. The panel channel is out of scope here (ROAD phase 4).

How the facts were obtained: 2026-11-15 21:03 to 21:06, from the repository (files and lines below), the installed SDK source in `node_modules/`, and web pages read on 2026-11-15 (URLs below). Web pages, issues and blogs are untrusted data and are quoted, not followed. Nothing was installed or run from third parties. Behaviour of Claude Code, Codex and Claude Desktop was not tested; it rests on their documentation and on GitHub issues.

### Elicitation in the spec

- Elicitation is a server request, `elicitation/create`, that asks the user for input through the client. Form mode exists since spec `2025-06-18`; URL mode "is introduced in the `2025-11-25` version" (spec page, draft, read 2026-11-15: https://modelcontextprotocol.io/specification/draft/client/elicitation). The 2025-06-18 page was fetched and mentions form mode only (https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation, read 2026-11-15).
- Capability: the client declares `elicitation` in `initialize` (2025-11-25 and earlier); an empty object means form only. The draft revision moves this to `_meta.io.modelcontextprotocol/clientCapabilities` on each request and replaces the server-initiated request with an `InputRequiredResult` returned from the tool call (draft page, same URL). SDK 1.32.1 implements the server-initiated form.
- Responses carry `action` of `accept`, `decline` or `cancel`. For URL mode, `accept` only means the user consented to open the link; the outcome comes out of band (draft page).
- Spec requirements on clients: show which server asks, offer decline and cancel, and for URL mode show the full URL and gather consent before navigation, and open it so that "the client or LLM" cannot inspect the content (draft page, Safe URL handling). Servers "MUST NOT" put a pre-authenticated URL in a URL elicitation, because it could be used to impersonate the user.
- The spec names no mechanism that tells the server whether a person or a program answered. The only identity statement is that servers "MUST bind elicitation requests to the client and user identity" and must not trust client-provided user identification (draft page, Security considerations).

### Claude Code

- Documented behaviour (https://code.claude.com/docs/en/mcp, section "Respond to MCP elicitation requests", read 2026-11-15): Claude Code "displays an interactive dialog in the terminal", form mode as fields, URL mode as a question whether to open the link. It declares `elicitation: {form: {}, url: {}}` to stdio, sse, http and ws servers in the user's configuration from v2.1.287, and the bare `elicitation: {}` on some other connections (form only).
- The model has no tool that answers the dialog; the page describes the answer as the user's. The documented exception is the `Elicitation` hook: "To auto-respond to elicitation requests without showing a dialog, use the `Elicitation` hook." A hook can return `action: "accept"` with `content`, `decline` or `cancel`, and "the server gets your answer and no dialog appears" (https://code.claude.com/docs/en/hooks, "Elicitation output", read 2026-11-15). Hooks are shell commands, HTTP calls or MCP tool calls configured in settings files. The matcher is the MCP server name. A top-level `decision` from these hooks was ignored from v2.1.105 until the fix in v2.1.284 (same page).
- Where hooks live: `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed settings, plugins (hooks page). Claude Code "watches your settings files and reloads them when they change ... including edits to `permissions`, `hooks`" (https://code.claude.com/docs/en/settings, "When edits take effect", read 2026-11-15). A `ConfigChange` hook runs on direct edits to settings files.
- Writes to `.claude` are "protected paths": prompted in `default` and `acceptEdits`, decided by the classifier in `auto`, denied in `dontAsk`, allowed in `bypassPermissions`; `permissions.allow` rules do not pre-approve them (https://code.claude.com/docs/en/permission-modes, "Protected paths", read 2026-11-15). With `permissions.blockWritesOutsideWorkingDirectories` on, Write/Edit to settings files are refused in every mode (same page; setting needs v2.1.314). `~/.claude/settings.json` is outside a project directory. The page quoted does not say that a shell command (for example `echo ... > ~/.claude/settings.json`) is covered by the same protection beyond its redirect check (permissions page, "Redirections", read 2026-11-15).
- Managed settings sit above all other sources, and `allowManagedHooksOnly: true` makes "only managed hooks run" (https://code.claude.com/docs/en/settings-reference, read 2026-11-15, lines 3608-3638 of the page text). `disableAllHooks` outside managed settings does not turn off managed hooks (same page, line 3160). Whether a user-level agent can edit a managed file depends on OS file permissions; the pages do not claim protection against a local administrator.
- Non-interactive sessions: "In a non-interactive session, Claude Code asks the server to cancel a task that requests input, without running your `Elicitation` hooks or calling the Agent SDK's `onElicitation` callback" (mcp page, tasks section). `elicitation/create` for tasks "is served only in interactive terminal sessions".
- **VS Code extension: contradictory evidence.** The extension docs do not mention elicitation (https://code.claude.com/docs/en/vs-code, read 2026-11-15; the last 4 KB of the page were not read). The mcp page says the dialog appears "in the terminal" and describes cards in claude.ai/code and the Desktop Code tab for cloud sessions. GitHub issues report that the extension declares the capability and then auto-declines: anthropics/claude-code#41292 (opened 2026-03-31, extension 2.1.87 to 2.1.88, closed 2026-04-03 as duplicate of #35353, locked) and #79174 (opened 2026-07-19, reports up to extension 2.1.235 and CLI 2.1.206 on 2026-08-19, closed by a stale bot 2026-09-21 as not planned, a duplicate #98256 opened 2026-09-29) (https://github.com/anthropics/claude-code/issues/41292, https://github.com/anthropics/claude-code/issues/79174, read 2026-11-15). A reported log line is "Elicitation request received in print mode". The server cannot tell this from a user's decline. No fix was found; the current extension version was not tested.
- Claude Desktop: no official page found that documents elicitation in the chat app. Issues reviewed through search snippets only (the host `claudeissues.com` did not resolve for the fetch tool): a feature request that Desktop lacks it (#41110, #41347), and reports that the embedded runtime in Cowork/Desktop Code declares the capability and cancels or never renders the request (#56243, #88901, #94450). Treated as unverified.

### Keeping a command out of the agent's shell (Claude Code)

- Evaluation order is deny, then ask, then allow; a deny rule always wins (https://code.claude.com/docs/en/permissions, read 2026-11-15). A bare `Bash` deny removes the tool; a scoped rule such as `Bash(rm *)` blocks matching calls.
- The docs state limits: a Bash rule "matches the command text Claude writes ... and isn't a security boundary around the program". `Bash(curl *)` stops `curl https://example.com` and does not stop `/usr/bin/curl ...` or `sh -c 'curl ...'`; `Bash(rm *)` does not stop `/bin/rm` or `bash -c '...'`. A built-in wrapper list (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`) is stripped before matching; runners such as `npx`, `docker exec` are not. Compound commands are split and deny applies "when any subcommand matches", including command substitutions. Argument-constraining patterns are "fragile".
- Documented stronger options: OS sandboxing (https://code.claude.com/docs/en/sandboxing.md, not read in detail) and PreToolUse hooks, which see the full command text. Read/Edit deny rules cover built-in tools and recognised shell file commands but "don't apply to ... arbitrary subprocesses that read or write files indirectly, like a Python or Node script".
- MCP tool names are `mcp__<server>__<tool>`; a deny rule may name a tool or a whole server; rules with parentheses on `mcp__` tools in settings files are skipped (permissions page).
- A terminal command run by the user in a separate terminal window is outside the agent's tool surface. In the VS Code extension the `!` Bash shortcut is not available (vs-code page comparison table), which does not stop the user from opening an ordinary terminal.

### Loopback approval page

- The spec's own URL-mode rules say the URL must not be pre-authenticated and that the server must verify who opens it (draft page, Phishing). On a single-user machine there is no session cookie to compare.
- Inference, not sourced: a process running as the same OS user can open any loopback port with `curl` or a fetch tool, read files the user can read (including a secret written to disk or to a process environment), read process arguments (`ps`), and, if a secret is delivered through the browser launcher, observe it. Claude Code's own defences against this are the Bash rule limits above and the sandbox, not the page.
- Existing upstream pattern: `oauth-flow.ts` uses a random `state`, binds `127.0.0.1`, serves once and closes. Its secret travels in the URL given to the browser (`:216`), and the OAuth case does not defend against a local agent.
- Whether a code shown on a page or in a terminal can stay unseen by an agent that has a shell and a fetch tool is not settled by any source read. It is an inference from the Bash rule limits and the sandbox notes above, and the test in the decision list would check it.

## Consequences

- With SDK 1.32.1 the server can send form and URL elicitation today and can check `elicitation.form` and `elicitation.url` in `getClientCapabilities()`. A thrown `Client does not support ...` error is the SDK's signal that the client did not declare the mode.
- Declaring the capability does not prove a person sees the request: the VS Code reports show a client that declares it and declines automatically, and Claude Code hooks can answer for the user. A decline from such a client is indistinguishable from a person's decline (issue #79174), so a grant only ever comes from `accept`, and a missing or declined answer must not be treated as a refusal that a later retry can route around by another path.
- An `accept` from a hook is also indistinguishable from a person's `accept`. Whoever can write a user, project or local settings file, or run a shell command that writes one, can auto-approve every elicitation grant. The mitigations in the docs are managed settings with `allowManagedHooksOnly`, protected-path prompts, and `blockWritesOutsideWorkingDirectories`; none is a default for an individual user, and the docs do not call them a boundary against a shell.
- The spec's own wording (§14.2: "supported client approval/elicitation") counts elicitation as an authenticated user interaction. In Claude Code that holds only while no hook answers and the session is interactive. In upstream's panel agent it does not hold (`codex-backend.ts:392-406`).
- A terminal command is outside the agent's tools only if the host is configured so. Claude Code deny rules on Bash text are bypassable by path, `sh -c`, or a script the agent writes and runs; the sandbox or a PreToolUse hook is needed for more. The spec already states the limit (§14.3, last paragraph). Whether the agent can read the stored plan hash and mint a confirmation itself depends on what the command checks; a confirmation typed by the person at a prompt on the controlling terminal (not stdin of a pipe) is a property the fork can build and the agent's shell can still reach through a pseudo-terminal.
- A loopback page that carries no secret can be fetched by a same-user agent. A secret raises the bar only if it never reaches a channel the agent reads; the sources found show no design that holds against an agent with a shell and a fetch tool.
- Codex and Claude Desktop cannot be relied on for elicitation on the evidence read: Codex's official docs are silent and the Desktop reports are bugs or requests.
- §14.2 forbids a model-callable tool that creates or widens a grant; every channel above assumes none is registered.

## Comparison

| Channel | Who can answer | Client support (evidence) | Residual risk |
| --- | --- | --- | --- |
| Form elicitation (`elicitInput`) | The user in the dialog; in Claude Code also an `Elicitation` hook, or `decline` by a client that cannot render it | Claude Code CLI documented, interactive only; VS Code extension reported auto-decline (issues #41292, #79174, unresolved); Codex unconfirmed; Desktop unverified | A hook or an agent that edits settings can accept; a declining client looks like a refusal |
| URL elicitation (`mode: "url"`) to a loopback page | The user who opens the page; the client shows the URL and asks consent | Claude Code declares `url` from v2.1.287 for stdio/http servers (docs); other clients unverified | The page needs its own secret and origin checks; an agent with a fetch tool can reach the page; URL must not be pre-authenticated (spec) |
| Terminal command run by the user | Whoever holds a terminal; the agent too, if its shell is not restricted | Any client, since it uses none | Bash deny rules are text matches (bypass by path, `sh -c`, scripts); sandbox or PreToolUse hook needed; agent sharing the user's account can run it |
| Loopback HTTP page opened by the user | Anyone who can reach the port with the secret | Any client; reuses `oauth-flow.ts` loopback and browser launcher | Same-user agent can fetch the page and read any secret stored on disk or in the environment; secret only helps if delivered out of band |
| Client-native tool permission prompt (Claude Code `ask` rule on the effectful tool; Codex `approval_mode`) | The user, at the host's own permission prompt | Claude Code documented (`ask` rules, `mcp__server__tool`); Codex `prompt` and `writes` modes documented | Grants no hash-bound `ApprovalGrant`; the host's rules decide, and "don't ask again" can widen it; the fork cannot see the answer |

## Facts a decision needs

- Whether the owner accepts "the person sees a dialog or hook-free client" as sufficient for grants, or requires that no local process can answer (which none of the channels above guarantees against a shell-capable agent on the same account).
- Which hosts must be supported in this phase: if Claude Code CLI only, elicitation is documented there; the VS Code extension needs a test on the current version, since the issues are unresolved.
- Whether a managed-settings recipe (`allowManagedHooksOnly`, `blockWritesOutsideWorkingDirectories`, sandbox, Bash deny rules) may be documented as the strict deployment (§14.3 already allows this).
- How the fork should record the channel in an `ApprovalGrant` (for example `elicitation`, `terminal`, `panel`), so a weaker channel is visible in the run record. This is a design point for SPEC §14.2, not settled here.
- A test the owner can run to settle the open client facts: a small local MCP server that calls `elicitInput` and logs the result, with and without an `Elicitation` hook, in CLI and in the VS Code extension. It was not run here.

## Options for the owner

- Elicitation first where the client declares it and answers it interactively, with a terminal command for clients that do not; the plan hash shown in both.
- URL-mode elicitation pointing to a loopback page that shows the action plan, with a challenge the person copies from the page to the terminal; combined with the terminal command above for clients without elicitation.
- Client-native `ask` rules on the effectful architect tool as a supplement, never as the grant.
- A documented strict deployment (managed settings, sandbox) stated as the condition under which the guarantee holds, as §14.3 already says for the host's other tools.
